# 小米手环 10 与 OPPO 健康共存

本 Fork 基于上游提交 `1ccdda52ec959587c698926e79b73236103c235f`。当前版本 `1.8.7-coexist.6` 修复旧睡眠阻塞其他数据、半段睡眠无法补长和新版控制中心默认图片及无效入口，增加本机运动摘要补读。保留两版 OPPO 共存、设备页数据入口、按连接归属隔离控制及 DRS 启动修复；实际手机展示仍需核对。

## 能做到什么

新增实验性共存模式，默认开启。小米运动健康保持启用，继续负责手环蓝牙连接、通知、天气、表盘、固件升级、NFC 等设备功能。桥接监听其正常接收的健康文件，将文件复制到本机，再复用上游解析、去重和 OPPO 健康写入流程。

```text
小米手环 10 → 小米运动健康 → 桥接本机副本 → OPPO 健康
                 │
                 └─ 继续负责蓝牙连接与设备设置
```

两个 App 可以保留并打开使用；本实现采用一个 App 管理连接、另一个 App 读取同步副本的方式。它没有让两个 App 同时建立独立的手环控制连接，也没有实现双向数据同步。

| 内容 | 本版行为与边界 |
| --- | --- |
| 小米运动健康 | 共存流程不执行强停或禁用小米 App 的命令；仍使用其原有同步流程 |
| 步数、心率、静息心率、血氧、压力、睡眠等 | 支持上游解析器和 OPPO 写入器能识别的文件格式；具体手环固件和 OPPO 展示效果待真机验证 |
| 运动记录 | 复用上游运动文件解析；不同运动类型和详细轨迹不保证全部覆盖 |
| 连接状态、电量 | 观察小米 App 的连接事件和电量响应；并非桥接另建连接读取 |
| 小米 App 内已有历史 | 补读已下载的睡眠、步数、心率、血氧、压力及常见运动摘要；只读选中账号和手环。轨迹暂不补导入 |
| OPPO → 小米 | 未实现；在 OPPO 手工添加或修改的数据不会反向进入小米 App |
| 表盘、OTA、NFC、天气、手环通知 | 继续在小米 App 中操作；共存时桥接停止 OPPO 侧重复控制转发。控制中心点手环打开 OPPO 健康原生面板 |
| 云端数据 | 本次没有验证任何账号的云端上传、下载或两家云端互通 |

原有独占接管模式在旧适配版本仍保留。6.10.12 当前只适配共存，添加/重连入口会要求开启共存后继续，避免进入尚未适配该版的独占控制路径。

## 安装与使用

1. 先在小米运动健康中登录并正常绑定小米手环 10，确认它可以连接和同步。保留系统蓝牙配对。
2. 安装本 Fork 构建的模块 APK。模块沿用上游包名，但使用本地 Fork 签名，不能直接覆盖使用另一签名的上游模块；若已安装上游模块，应先备份所需模块数据再换装。两个健康 App 本身保持原版即可。
3. Xposed 框架须支持 **libxposed API 102**，例如支持该 API 的 Vector；仅有较旧的 LSPosed 并不足以证明能加载本模块。作用域勾选 `com.mi.health`、`com.heytap.health`、`com.heytap.mydevices`。共存期间始终保留小米运动健康的作用域。`com.coloros.alarmclock` 用于上游时钟功能，共存数据复制本身不依赖它。
4. 首次启用作用域后重启手机，或手动强停并重新打开相关 App，使 hook 生效。在 Root 管理器中授权「小米手环桥接」。
5. 打开桥接：检查 Root → 导入绑定 → 保持「与小米运动健康共存（实验）」开启 → 添加到健康。若以前由模块独占接管，进入此流程会先结束桥接直连，并恢复由模块禁用的小米 App。
6. 打开 OPPO 健康，完成登录并进入首页，让桥接取得当前 OPPO 账号；然后在小米运动健康中连接并同步手环。界面打开或蓝牙重新连接本身不保证手环会重传已被官方 App 消费的历史文件。
7. 打开 OPPO 健康检查对应日期的数据。日常保持小米运动健康的后台连接、蓝牙权限和其原有通知权限。共存模式无需桥接另取一条蓝牙连接，也无需为数据复制额外开启 OPPO 的通知使用权。
8. 在桥接首页「功能」中点「一键同步到 OPPO 健康」，会启动两个健康 App。首次读取本机全部历史，之后检查新增及最近七天；中断后续传。后来在小米 App 下载了更早的云端记录时，点「重新补齐全部历史」，重新扫描并去重。进度分别显示已读源记录、睡眠段数、新增测量、OPPO 写入阶段、待写点数及睡眠处理天数。「本机读取完成」与「OPPO 当前一轮写入结束」分开显示，仍须核对对应日期的实际页面。

从本 Fork 旧版本覆盖升级到 `coexist.6`，保持模块数据和绑定，更新后重启手机使两家 App 的所有进程加载新 hook。OPPO 健康升级后完成正常登录和隐私确认，再点同步；无需清空健康 App 数据。本次升级会自动重新检查一次本机历史，修复先前未完成的睡眠并补读运动摘要；已保存测量保持，读取计数会重新开始。后续正常同步继续使用增量范围。

本机没有下载的云端旧记录无法由此入口直接取回。先在小米 App 打开相应历史日期、等待数据和睡眠明细加载，再回桥接重新补齐全部历史。只有睡眠总时长、缺少分期且无法确认清醒时长的记录会跳过，避免把清醒时间计为睡眠；调试状态会记录 `MI_HISTORY_SLEEP_DETAILS_REQUIRED`。账号不一致时重新导入当前绑定。队列满时保留未消费行；OPPO 确认一批后自动唤醒读取。写入失败时显示错误并重试，不把打开 App 本身算作已补齐。

OPPO 健康里的数据会受实际同步时机、账号状态和已支持的文件类型影响。建议先核对一次步数、一次新测心率和次日睡眠，再决定是否作为日常使用方案。

## 实现依据

- 小米 `classes10.dex`：`com.xiaomi.fit.fitness.device.mi.receive.FitnessReceiverHandler.handleDataInternal(String, int, byte[])` 在类型 `102` 时将带设备 DID 的原始分片交给 `FitnessDataReceiver.onReceive(byte[])`。
- 生态设备分支的接收方法名为 `handleData(String, int, byte[])`，分别安装 hook。
- 官方接收器的分片头为两个小端 16 位数：总片数和片序号。完整文件包含 7 字节文件 ID 和 CRC32，和上游 `BandHistoryParser.acceptFragment` 的输入一致。
- 在官方接收函数执行前复制分片；最后一片在桥接完成本机持久化后返回。原始参数、返回值和官方确认行为保留。镜像不可用时允许官方函数继续运行，不阻断其同步。
- 小米 `classes3.dex`：从 `WearApiCall` 获取选中设备的 DID、地址、固件和连接事件，观察电量回包；不发送新的蓝牙控制命令。
- 桥接 Provider 验证来访 UID 属于 `com.mi.health`，只接受已登记设备的 DID/地址；开机后用户存储首次解锁前暂停，独占模式或移除登记后停止接收。每个分片最多 128 KiB，完整文件复用上游 1 MiB 限制。
- OPPO 的账号、数据 API、插入/读取选项、点数据模型、步数/睡眠/运动模型和设备页入口通过 DEX 签名核对。`SyncObserver.dispose()` 由父类提供，按实际继承链核对。
- 复用已有的文件归档、记录 ID、版本去重和原生数据读回确认；没有改写两家原始 APK，也没有导出用户账号凭据。

异常或进程退出可能令正在接收的文件缺少分片，新文件第一片会重置解析器。镜像不可用时小米仍可能完成确认，因此无法保证该文件以后会自动重传。这也是本版保留实验标记的原因之一。

### coexist.6：避免整段历史占住写入线程

用户新日志中，队列已达到 32768 点、确认 0 点，而 OPPO 仍在处理第 170 / 446 天睡眠。`coexist.5` 修复了通知导致的重读，但仍在一个写入任务内先遍历全部睡眠，再处理心率、活动与运动；没有避免跨类型阻塞。

- 点数据、活动、运动、睡眠依次各处理一小批。点数据每轮最多 20 页 / 4000 点，其他类型最多 3 天或 3 次运动；达到约 3 秒后，在当前操作结束时让出下一类型。单次宿主 API 调用仍可能超过该时间，6.10.12 调用最多等待 15 秒后保留并重试。
- 写入失败只对该类型设置等待时间，其他类型继续。旧压力清理也分批执行。队列读页先处理新加入的点，已确认后仍逐条匹配账号和版本再移出队列；没有扩大上限或丢弃旧数据。
- 使用 WAL 让进度读取可以在补读事务尚未提交时读取已提交快照。正常的多个写入事务仍由 SQLite 串行处理，不能据此保证消除所有锁等待。
- 睡眠、活动与运动保留当前进程的分批计划；输入变化时重新核对，已确认且未变化的日期不重复写。活动分钟和运动写入缓存按 OPPO 账号隔离。睡眠完整记录可以补长原先未完成的区间，同阶段的尾部也可以补长；完整实时点值继续保留，较短旧记录不能覆盖较长记录。
- 每日活动缺少正式日报热量时，汇总源分钟记录中已有的热量；已有日报值保持优先。步数、热量、距离按实际源数据写入，缺少的站立小时和锻炼分钟不会从普通走路分钟中编造。
- 新增 `sport_report` 只读补导入，依据原 APK 的 `SportReportEntity`、`SportBasicReport` 和 `SportReportBaseParser` 字段，映射已支持的跑步、健走、骑行、登山、徒步、游泳、自由活动、跳绳等摘要。保留原始时刻、时区和已有的距离、热量、时长、平均心率、步数；未知类型明确跳过，轨迹及缺失的分项不编造。
- 升级首次重查本机历史，随后保留七天重叠的增量同步。6.10.12 原生面板按真实 MAC 替换图片；有缓存时用小米机身图，否则用系统手环图标。隐藏 OPPO 表盘、系统升级等无效行及表盘预览区，保留原生电量与打开 OPPO 健康入口。

用户尚未给出缺失睡眠的具体日期，因此本次修复针对已复现的“已有半段导致完整历史被去重跳过”，不能据此确认截图设备上的每一段睡眠已恢复。首次大批量历史仍需写入和读回确认，不能承诺瞬间完成。

### coexist.5：入口、队列与同步进度

- 控制中心的设备详情请求转交 OPPO 自己解析出的原生面板；不再因共存而自动打开小米 App。6.10.12 的连接回调也不再打开小米。原生面板按当前手环的 MAC / 设备 ID 投影电量及连接状态，不改动其他设备。
- 6.10.12 的设备页心率、睡眠、日常活动、运动记录、血氧、压力菜单原本进入监测设置。针对桥接手环改为对应的 OPPO 原生历史页面；页面没有记录时仍需看实际导入进度。
- 读取请求和进度通知使用平级 URI，避免 Android 将父级通知送到子级观察者而不断重启读取。队列容量释放通知与测量变更通知分开，确认点数据不再触发全量历史重放。
- 小米页最多 256 行 / 192 Ki 字符，一页一次保存事务和容量汇总；单个源行容量不足时整行保留。OPPO 每页最多 200 点，原生读回确认后一次批量回执，只删除该账号的对应版本。不是清空队列或丢弃旧数据来提速。
- 睡眠按新日期优先写入，点数据确认不再触发睡眠全库重扫。睡眠、步数或运动有未确认记录时保留失败状态并重试，不再报告本轮全部完成。导出日志新增 `oppo-import` 的阶段、待写点数、已确认点数和睡眠进度。
- 主同步首次补读全部本机历史，后续使用每张表的完成截止时刻并重读七天，以处理近期补充记录。账号或设备变化时重置范围；「重新补齐全部历史」保留查找更早下载记录的入口。删除源数据不会反向删除 OPPO 记录。

### coexist.4：历史记录与设备控制归属

## OPPO 健康点开闪退时

`mirror file PARSED` 只能说明健康文件到达桥接，不能证明 OPPO 页面正常启动或已完成数据写入。旧导出里的 `live-status` 是独占连接服务最后保存的状态，也可能早于当前共存会话。

`coexist.2` 的日志头会重新读取当前所有权、登记状态和模块版本；旧服务状态标为 `last-direct-status`。导出末尾新增 `OPPO Health Android crash buffer`，通过已授予的 Root 权限读取 OPPO 健康 UID 的 Android crash buffer，最多 240 行、128 KiB。读取有 8 秒超时，临时文件保存在模块私有缓存并在读取后删除。导出不会清除崩溃缓冲区、健康 App 数据或账号。

收集方法：覆盖安装 `coexist.2` → 再打开 OPPO 健康复现闪退 → 回到桥接的「帮助 → 发送调试日志」。如果末尾显示 `HEALTH_CRASH_BUFFER_EMPTY`，说明这次读取没有取得崩溃行；`HEALTH_CRASH_LOG_UNAVAILABLE` 则表示日志读取未完成。此时需要框架日志或 ADB 崩溃记录，不能仅根据镜像接收日志判定原因。

### coexist.3：DRS 空上下文修复

用户 2026-10-29 提供的崩溃缓冲区包含 8 次相同的启动崩溃：`ES#Track` 线程在 `CapacityGovernor.init:204` 对空的应用上下文调用 `getSharedPreferences`。输入日志确认当时 `mode=COEXIST registered=true coexistReady=true`，因此旧 `last-direct-status` 不能解释这次闪退。

对提供的 OPPO APK 定点反编译后确认：`TrackApiImpl.checkInit` → `TrackApi.staticInit` → 本地 DRS → `DrsCore.initCapacityGovernor` → `CapacityGovernor.init`；最后一步直接使用 `context.getApplicationContext().getSharedPreferences(...)`，没有空值处理。DRS 的存储上下文可能来自 `createDeviceProtectedStorageContext()`。原模块在 `Application.attach` 完成后即加载会访问宿主单例的 hook，此时应用上下文尚可能未由 Android 发布；这属于可能影响触发的启动时序因素，尚未在用户设备上单独复现排除。

修复包含两项：

- 在上游 `DrsCore.init(Context)` 入口、DRS 缓存应用上下文之前，只对 `getApplicationContext()` 返回空的上下文包装应用查找结果，使用 OPPO 自己的 `GlobalApplicationHolder` 中已附加的 `Application`。其文件、数据库及存储保护域继续委托原存储上下文；健康的数据文件不在此处更换。
- 提前安装这一个上下文防护 hook，其余 OPPO hook 等 `SportHealthApplication.onCreate` 成功返回后再加载。账号恢复改为安装后主动调度，兼顾原有热重载。

Android 环境回归测试使用真实 `ContextWrapper` 和设备保护存储上下文，重现 APK 中的两步空指针调用；同时检查修复后可读取设置、原存储域保持、正常上下文保持原样。测试验证该故障模式，不等同于用户手机上的完整 OPPO App 启动验证。
